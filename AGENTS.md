# Инструкции по работе с проектом

## Общие правила

Это существующее приложение на Python/PyQt.

Во время рефакторинга текущее поведение приложения должно сохраняться.

Предпочитай небольшие и точечные изменения вместо масштабного переписывания кода.

Сохраняй существующую архитектуру проекта, если нет серьёзной технической причины её менять.

Не выполняй рефакторинг кода, который не относится к текущей задаче.

Не изменяй публичные сигнатуры функций и методов без необходимости.

Не добавляй новые production-зависимости без явного разрешения пользователя.

Не переписывай работающий код только ради изменения стиля или использования другого подхода.


## Текущая область работы

Текущий этап разработки посвящён только рефакторингу приложения.

Цели текущего рефакторинга:

- повысить стабильность приложения;
- уменьшить вероятность ошибок;
- улучшить обработку исключений;
- устранить потенциальные проблемы с потоками PyQt;
- уменьшить блокировки пользовательского интерфейса;
- повысить производительность там, где существуют реальные узкие места;
- уменьшить избыточное дублирование кода;
- улучшить сопровождаемость;
- улучшить тестируемость;
- упростить слишком сложные участки кода.

## Сохранение поведения приложения

Рефакторинг должен по возможности сохранять текущее функциональное поведение приложения.

Если предлагаемое изменение способно изменить пользовательское поведение, формат выходных данных или результаты вычислений, обязательно сообщи об этом до реализации.

Не меняй:

- формат существующих Excel-файлов;
- структуру выходных файлов;
- названия существующих колонок;
- публичные интерфейсы между модулями;
- пользовательский интерфейс;

если этого прямо не требует текущая задача.


## PyQt и многопоточность

Особое внимание уделяй архитектуре PyQt.

Проверяй:

- тяжёлые операции в основном GUI-потоке;
- синхронные операции, блокирующие интерфейс;
- жизненный цикл QThread и worker-объектов;
- корректность сигналов и слотов;
- повторный запуск фоновых операций;
- обработку исключений внутри worker;
- корректное завершение потоков;
- очистку ресурсов;
- состояние приложения после возникновения ошибки;
- потенциальные race conditions;
- доступ нескольких потоков к общему состоянию.

Тяжёлые вычисления и операции ввода-вывода не должны без необходимости выполняться в основном Qt-потоке.

Не изменяй существующее поведение интерфейса только ради стилистической чистоты кода.


## Производительность

Не выполняй оптимизацию только на основании предположения, что определённый код является медленным.

По возможности используй последовательность:

1. найти потенциальное узкое место;
2. измерить его;
3. определить причину;
4. предложить изменение;
5. выполнить изменение;
6. повторно измерить результат.

Особое внимание уделяй:

- повторному чтению одних и тех же файлов;
- лишнему чтению Excel;
- ненужному копированию DataFrame;
- избыточному использованию DataFrame.apply;
- DataFrame.iterrows и другим потенциально медленным циклам;
- многократному выполнению одинаковых вычислений;
- созданию крупных временных объектов;
- избыточному потреблению памяти;
- блокирующим операциям Excel;
- повторной обработке изображений;
- ненужным преобразованиям между NumPy, Pandas и Tensor;
- лишнему переносу данных CPU → GPU и GPU → CPU.

Не заменяй понятный код на более сложный ради незначительного или недоказанного прироста производительности.


## Стабильность

Ищи потенциальные проблемы:

- необработанные исключения;
- исключения, которые подавляются без логирования;
- слишком широкие конструкции try/except;
- некорректное состояние приложения после ошибки;
- незакрытые файлы;
- незакрытые ресурсы;
- утечки памяти;
- неправильный жизненный цикл потоков;
- гонки между потоками;
- небезопасный доступ к общим данным;
- повторное выполнение одной и той же операции;
- некорректную очистку состояния после неудачной операции;
- отсутствие проверки входных данных;
- ситуации, когда ошибка скрывается и приложение продолжает работать с неправильными данными.


## Архитектура и рефакторинг

Не переписывай модуль только потому, что его можно организовать иначе.

Каждый рефакторинг должен иметь конкретную пользу.

Допустимые причины рефакторинга:

- повышение стабильности;
- устранение реальной ошибки;
- уменьшение дублирования;
- снижение связанности модулей;
- разделение слишком большого количества обязанностей;
- упрощение сложного control flow;
- улучшение тестируемости;
- повышение производительности;
- улучшение диагностики ошибок;
- уменьшение вероятности появления новых ошибок.

Избегай over-engineering.

Не вводи дополнительные абстракции, классы, сервисы, фабрики или слои архитектуры без реальной необходимости.

Предпочитай минимальное изменение, которое решает обнаруженную проблему.


## Работа с существующим кодом

Перед изменением функции или класса:

1. найди все важные места использования;
2. определи связанные модули;
3. оцени возможное влияние изменения;
4. проверь существующие тесты;
5. только после этого изменяй код.

Не удаляй код только потому, что он кажется неиспользуемым.

Сначала убедись, что на него нет:

- динамических вызовов;
- сигналов PyQt;
- callback;
- импорта из других модулей;
- вызовов через UI;
- использования в тестах;
- использования в конфигурации.


## Тестирование

После каждого реализованного изменения:

- запускай относящиеся к изменению тесты;
- по возможности запускай полный существующий набор тестов;
- сообщай обо всех упавших тестах;
- отделяй существующие до изменения ошибки от ошибок, появившихся после изменения.

Для исправления ошибок по возможности добавляй regression test, который:

1. воспроизводит старую проблему;
2. проходит после исправления.

Не изменяй тесты только для того, чтобы заставить неправильную реализацию проходить проверки.


## Git

Без отдельного явного разрешения пользователя запрещено:

- выполнять git push;
- выполнять merge;
- выполнять rebase;
- переписывать Git history;
- удалять ветки;
- создавать commit;
- менять remote;
- выполнять force push.

Перед завершением любой задачи с изменением кода:

1. выполни git diff;
2. проверь список изменённых файлов;
3. убедись, что не изменены файлы, не относящиеся к задаче;
4. перечисли пользователю каждый изменённый файл;
5. кратко объясни назначение каждого изменения.


## Формат отчёта о найденной проблеме

Для каждой существенной проблемы сообщай:

1. Приоритет:
   - Critical;
   - High;
   - Medium;
   - Low.

2. Файл.

3. Класс, функция или метод, если применимо.

4. Что сейчас делает код.

5. В чём заключается проблема.

6. Почему это может влиять на:
   - стабильность;
   - корректность;
   - производительность;
   - сопровождаемость.

7. Какое изменение рекомендуется.

8. Какой ожидается результат.

9. Каков риск изменения.

10. Можно ли полностью сохранить текущее поведение.

11. Нужно ли сначала добавить тест.


## Принцип работы

Для сложных и потенциально опасных изменений сначала выполняй анализ.

Если пользователь явно просит только исследовать проблему или провести аудит:

- не изменяй файлы;
- не выполняй рефакторинг;
- не исправляй найденные проблемы;
- сначала представь результаты анализа и предложенный план.

Изменения выполняй только тогда, когда пользователь явно попросил перейти к реализации.
