# Переиспользуемый факт аналитического заказа

`STAT-FACTS-REUSE-01`. Контракт политик: [statistics_purchase_contract.md](statistics_purchase_contract.md).
Новая операция не подключена к production-драйверу и не выполняет клиентскую
агрегацию, RFM, чтение истории или запись файлов.

## Интерфейс и идентичности

```python
fact = build_purchase_order_fact(
    lines,                          # уже адаптированные позиции одного снимка
    identity_space=identity_space,  # пространство одного источника/поколения
    customer_id=canonical_customer,
    order_id=selected_order_id,
    order_datetime_utc=ordered_at,
    check=check,
)
```

`PurchaseOrderFact` — frozen/slots-структура: приватные идентичности клиента и
заказа, явное пространство ID, проверенная UTC-дата, результаты `strict` и
`extended`, компактные счётчики групп статусов. Raw, товары и позиции не сохраняются.
`repr` факта не выводит идентичности. Факт нельзя помещать в пользовательский DTO,
экспорт, журнал или постоянный кеш индивидуальных покупок.

REFERENCE передаёт уже канонический customer ID после CustomerMerges; INDEXED —
локальный SID в принятом вызывающим кодом представлении. Пространство задаётся
явно, например `REFERENCE:<snapshot>` или `INDEXED:<generation>`. Построитель не
преобразует ID и не загружает граф объединений. Будущий накопитель обязан принимать
факты только своего identity_space: одинаковые SID разных поколений не идентичны.

Дата должна быть timezone-aware UTC; функция не фильтрует и не нормализует период.
Выбор периода и снимка, валидация источника и единое пространство идентичностей —
ответственность вызывающего кода. Отсутствующая/некорректная идентичность или дата
вызывает безопасный ValueError без исходных значений в сообщении.

## Один проход позиций, две политики

Для каждой переданной позиции один раз вызываются `classify_status()` и
`eligible_purchase_policies()`. Количество проверяется существующим контрактом
STRICT/EXTENDED: положительное конечное целое, без округления. Цена валидируется
один раз и используется для обеих подходящих политик.

Каждый `PurchasePolicyResult` содержит `line_count`, `units`, `currency`, `amount`,
неизменяемый набор `monetary_issues` и признаки `has_purchase`/`monetary_available`.
`has_purchase` — bool: несколько позиций не превращают один факт в несколько
заказов. После выбора уникального снимка вклад в Frequency равен
`int(fact.strict.has_purchase)` либо `int(fact.extended.has_purchase)`.

Дедупликация не находится внутри факта. Повторный вызов функции с тем же заказом
создаст повторный факт: вызывающий код обязан использовать существующие
`OrderSnapshots`/`IndexedSnapshots`, а не суммировать все исходные снимки.
Первый снимок выбирается до проверки политик; Return в первом снимке не заменяется
позднейшим конфликтующим F ради покупки. Порядок чтения не равен бизнес-хронологии.

Нет вызовов InteractionBuilder или ProductResolver. Все переданные позиции
обрабатываются до товарного отбора; неразрешённый item ID не отменяет покупку.
Вычисления не зависят от остальных заказов: O(n) по позициям одного заказа,
O(1) дополнительной памяти, два числовых накопителя, до трёх валютных маркеров
в каждом и до восьми счётчиков статусных групп. Весь поток заказов не материализуется.
`check()` вызывается перед обработкой, на каждой позиции и перед возвратом факта;
отмена/ошибка callback распространяется без частичного результата.

## Денежные состояния

Переиспользуются `_currency()` и `_decimal()` из `order_statistics.py`:
`offline1C` → RUB, `kanzlerKz` → KZT; конечная неотрицательная числовая цена,
Decimal-арифметика. `price_of_line` — сумма позиции целиком, без умножения на
quantity, доставки, подстановки totalPrice/basePricePerItem и вычетов возвратов.
Строковая цена не принимается как числовая; преобразование строк из SQLite уже
выполнено существующим `IndexedInput.order()`.

| Состояние | has_purchase | currency | amount | monetary_available / issues |
|---|---|---|---|---|
| Нет принятых позиций | False | None | None | False, пустой набор |
| Известная нулевая сумма | True | RUB/KZT | Decimal(0) | True, пустой набор |
| Корректная сумма | True | RUB/KZT | Decimal | True, пустой набор |
| Неизвестная валюта | True | unknown | None | False, UNKNOWN_CURRENCY |
| Смешанные известные валюты | True | mixed | None | False, MIXED_CURRENCY |
| Непригодная/отсутствующая цена | True | Определяется независимо | None | False, INVALID_PRICE |

Причины могут сочетаться: например mixed и INVALID_PRICE. Известная часть суммы
не выдаётся за полную Monetary. Покупочный признак и дата сохраняются, даже когда
полная денежная оценка недоступна. Валюта определяется по принятым позициям каждой
политики отдельно: F в RUB и CP в KZT оставляют STRICT однозначной, EXTENDED — mixed.

Новая операция не перехватывает исходные ошибки адаптации. Если адаптер/проекция
не смогли предоставить позиции, их прежний fail-closed путь сохраняется. Передача
частично известной денежной информации напрямую в функцию — другой случай:
тогда неприменимость Monetary отмечается явно, без исключения покупки.

## Возвраты

На этой стадии ограничиваемся классификацией: `status_groups` и
`return_line_count` показывают возвратные позиции среди переданных строк.
Они не создают покупки и не корректируют суммы STRICT/EXTENDED. Отдельные суммы
и quantity возвратов отложены: для следующего покупательского агрегатора они не
нужны, а существующая проекция не сохраняет полные поля дробных позиций.
Количество возвратных адаптированных строк не является суммой денежных возвратов.

## Достаточность REFERENCE и INDEXED

REFERENCE предоставляет OrderLineRecord, INDEXED — SimpleNamespace из
`IndexedInput.order()`. Оба содержат status, quantity, namespace, price_of_line,
customer_id и order_datetime_utc. **У INDEXED-строк нет order_id**; нужный SID уже
есть в `raw['ids']['mindboxId']`. Поэтому идентичности и дата передаются явно из
выбранного заголовка/готовой канонической идентичности, без новой колонки или БД.
Это также позволяет построить факт пустого заказа.

Тесты используют один и тот же построитель в обёртках существующих точек адаптации
общего драйвера: повторных raw-проходов или адаптации для каждой политики нет.
Для сравнения пространств проверяется взаимно-однозначное соответствие клиентов
в обе стороны, в том числе aliases; исходные ID не сравниваются с SID напрямую.
Опубликованный индекс намеренно не хранит исходные таблицы соответствия ID.

Ограничения проекции:

- Дробные позиции исключаются из штатного адаптированного входа, их индексные
  status/namespace/price могут быть не сохранены. Это не теряет STRICT/EXTENDED
  покупки (они всё равно отвергают дробное количество), но не позволяет объявить
  статусные счётчики факта полной диагностикой всех исходных raw-позиций.
- Отсутствующая/нечисловая исходная priceOfLine приводит к adapter_bad; существующий
  `IndexedInput.order()` отклоняет такой заказ. Если будущая аналитика должна
  продолжать Frequency/Recency именно при этих исходных ошибках, понадобится
  отдельное минимальное решение для частичной проекции/адаптации. Нельзя обходить
  adapter_bad или достраивать сумму нулём. Это условное ограничение для ошибочных
  источников, а не недостаток данных корректно адаптированных заказов.
- Сохранённая отрицательная цена может дойти до адаптированных строк: новый факт
  отмечает INVALID_PRICE; прежний OrderAggregates продолжает отклонять её как раньше.

## Точка будущего подключения STAT-BUYER-AGG-01

В `_calculate_statistics()` сохраняются два охвата: legacy-пересечение Actions/Orders
и собственное покрытие Orders (`order_scope_period`). Накопителю нужно явно передать
исходный выбранный аналитический период (до normalize), покрытие Orders и пространство
ID. Не выводить период нового накопителя из нормализованного legacy analysis_filter.

1. **Внутри общего покрытия:** после `lines = adapted_lines(raw, eligible_lines)`,
   до `lines = tuple(line for line in lines if matches(line.product))`. Строить факт
   только для Orders-охвата и его первого снимка: действующий guard
   `scope_eligible` и отсутствие ключа в `scope_only_orders` уже различает этот случай.
   Нельзя безусловно добавлять факт на каждую legacy-адаптацию: ранний снимок мог
   быть выбран вне общего покрытия, и более поздний legacy-снимок станет дублем
   именно для нового аналитического охвата.
2. **Вне общего покрытия, но внутри покрытия Orders/исходного периода:** в ветви
   `if scope_eligible`, после проверки ключа против `snapshots.fingerprints` и
   `scope_only_orders`. Минимальная будущая правка — один раз сохранить результат
   `adapted_lines(raw, eligible)` в локальную переменную, передать те же строки
   построителю факта и `scope_order()`, затем продолжить существующую обработку.
3. Один факт передать одному будущему накопителю STRICT/EXTENDED; не создавать
   дедупликацию отдельно для политик и не повторять адаптацию или product resolution.

Существующие guards сохраняют первого владельца/снимок относительно Orders-охвата,
включая случай «сначала вне общего покрытия, затем конфликтующий внутри».
Диагностика одинаковых/конфликтующих снимков вне общего покрытия сейчас ограничена
множеством scope_only_orders без fingerprint. Если следующей задаче потребуются
такие счётчики для полного Orders-охвата, расширять выбор снимка у вызывающего кода
существующей логикой OrderSnapshots, сохраняя legacy-счётчики, а не внутри факта.

В этой задаче обе точки не изменены. Нет новых DTO, полей кеша, индекса, схемы БД,
поколений, алгоритмической provenance, GUI/XLSX/HTML или production PURCHASE.
При реальном подключении нужно включить оба новых модуля (политики и факты)
в алгоритмическую provenance и согласовать совместимость последующих агрегатов.
