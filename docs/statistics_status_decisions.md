Статусы означают:

- `AGREED_DIRECTION` — прямо согласованное направление пользователя. Это не разрешение реализовать его сейчас.
- `PROPOSED` — конкретная рекомендация DESIGN, подлежащая CONTRACT; не превращать в утверждённое правило.
- `BLOCKED_BY_DATA` — правило/возможность нельзя окончательно задать без фактической проверки; следующий этап требует отдельной задачи.
- `REQUIRES_APPROVAL` — отдельное решение пользователя после конкретизации данных/контракта/бюджета. Этот документ не запрашивает запуск дорогих операций.

Один статус отражает основное состояние решения; зависимости сохраняют дополнительные блокеры. Согласованное направление не понижается до вопроса из-за неизвестной реализации. Предложения новой схемы/алгоритма не становятся согласованными только потому, что пользователь потребовал подготовить дизайн.

## Зависимости и границы принятия

Критический путь: DATA02/03/04/05/06/07/08/09 → D09/D12/D14/D16/D28 → окончательные D11/D13/D15/D17 → CONTRACT D18/D19/D21 → синтетические CORE/INDEX/агрегаты/RFM/когорты/UI → D29. DATA01 отдельно закрывает metadata D27/уточнение каталога. Ранняя минимальная реализация может оставить некоторые capabilities недоступными, но не выдать недоступный lifecycle/refund/time за полную основную статистику.

Приоритетный минимум, не требующий нового бизнес-пересогласования: одна политика, F/sold/CP, delivering не purchase, historical purchase не стирается Return, Return-only ничего не восстанавливает, неизвестные CP units/money не0, старые отчёты прежние. Технические qualification/reconciliation/time/money/версионные решения по-прежнему открыты согласно таблицам.

В рамках DESIGN не выполнено ни одно действие будущих фаз. Исторические «решение не принято» из исходного аудита по D02–D06 закрыты новым заданием, но сам аудит не переписан. **Документы подготовлены; модель не объявлена полностью утверждённой.**
