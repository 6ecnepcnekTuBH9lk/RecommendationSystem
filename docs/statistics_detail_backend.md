# STAT-DETAIL-EXPORT-01B1 — backend и персональный RFM

Реализован backend без подключения GUI. Контракт 01A сохранён: Clients —
177 колонок, Orders — 23, OrderLines — 18; ровно четыре файла ZIP:
`clients.csv`, `orders.csv`, `order_lines.csv`, `manifest.json`.
Словарь колонок находится в [контракте 01A](statistics_detail_export_contract.md).

## Python API

```python
from datetime import date
from Application.statistics_detail_backend import export_detail_statistics
from Application.statistics_detail_contract import DetailPeriod, OrderMode

# Пример вызова для будущего caller; при разработке реальный экспорт не запускался.
result = export_detail_statistics(
    raw_root=canonical_root,             # каталог, содержащий canonical/
    destination=explicit_output_zip,     # явный путь вне репозитория/источника
    temporary_root=private_temp_root,    # заранее подготовленный private-каталог D:
    as_of_date=date(2026, 8, 31),         # UTC, весь день включительно
    event_period=DetailPeriod(date(2026, 1, 1), date(2026, 8, 31)),
    order_mode=OrderMode.ALL_SELECTED,
    progress=lambda event: update_stage(event['stage'], event['processed']),
    cancelled=lambda: cancellation_requested(),
    reserve_bytes=128 * 1024**2,
    max_temporary_bytes=8 * 1024**3,
)
# result.destination: Path; result.manifest: dict. repr не раскрывает содержимое.
```

Все аргументы keyword-only. `DetailPeriod()` означает отсутствие отбора событий,
но as_of всегда обязателен. Период включителен по датам UTC. `PURCHASE_EITHER`
выбирает заказы с покупкой по STRICT либо EXTENDED. Clients содержит ровно
владельцев выбранных Orders, включая владельцев непокупочных заказов при
ALL_SELECTED; контакты не определяют состав клиентов. Пустой результат даёт
три CSV с заголовками и manifest с нулевыми counts.

Возврат происходит после публикации и очистки состояния. Отмена — безопасный
`InterruptedError('Detail export cancelled')`. Остальные ошибки —
`DetailExportError` со служебным code. Только при невозможности очистки добавлен
`technical_path` собственного временного объекта. ID, имена и контакты не
добавляются в progress, manifest или сообщения исключений. Caller не должен
логировать CSV/DTO/словарь локальных переменных исключения.

## Источники, один проход и временные области

Удерживается существующий read-only `_reader_lock` canonical от проверки до
проверки ZIP. Нужен существующий непустой `canonical/.writer.lock`; backend
не создаёт lock-файл источника. Через catalog/effective_entries выбираются
доступные canonical Orders, через CustomerMerges строится штатный
CustomerIdResolver. Наличие CustomerMerges обязательно при доступных Orders;
его временное покрытие отдельно отражено в manifest, полнота не предполагается.

Каждая выбранная часть Orders читается один раз штатным iter_export. До
дедупликации проверяются дата исходного события firstAction и доступное покрытие,
после — единожды adapt_order и build_purchase_order_fact. Используется штатный
OrderSnapshots: first eligible snapshot, идентичные повторы пропускаются,
конфликтующий снимок блокирует экспорт, последний снимок не подменяет первый.
Его dictionary fingerprints заменён только SQLite-хранилищем; правило выбора
и семантический fingerprint не продублированы. Порядок исходных уникальных
заказов сохраняется ordinal.

Временная SQLite получает компактные PurchaseOrderFact всей доступной истории
до as_of, без raw Orders, и закодированные строки выбранных Orders/OrderLines.
Затем факты читаются из этой временной БД по одному покупателю в исходном
порядке; это не повторное чтение canonical Orders. buyer_metrics из 01A
вычисляет STRICT/EXTENDED, первую/вторую покупку, интервалы и наблюдаемую
когорту по всей истории. Первую наблюдаемую покупку нельзя трактовать как
первую покупку за всю жизнь. Период событий ограничивает только Orders/Lines
и состав Clients; история и RFM от него не зависят. Будущие события исключены.

Все строки выбранного заказа, включая возвраты, отмены, дробные/неположительные
количества, сохраняются по правилам 01A. Они не становятся покупками автоматически.
Пустой заказ получает строку Orders из header, без OrderLines. Временные FK
проверяются перед записью CSV; уникальные ключи не допускают дублирования.

## Персональный RFM и неизменность агрегата

В statistics_rfm_core добавлены empirical_ranks, RfmCustomerState и immutable
RfmObservation. RfmCustomerState оборачивает существующий RfmAggregates для
одного покупателя и выдаёт только скалярные наблюдения; внутренние _Buyer и
_Window наружу не передаются. Используются существующие _observation,
rfm_windows, rfm_score, rfm_segment. Тело RfmAggregates не изменено; формула
nearest rank вынесена в общую функцию без изменения арифметики.

DetailRfmStore сохраняет 12 наблюдений на покупателя: две политики × три
окна × RUB/KZT. База и пороги учитывают всех покупателей доступной истории
48M, в том числе не попавших в период экспортируемых событий. Денежные
значения хранятся текстом Decimal с числовым SQLite collation, без REAL.
Дисковые histogram B-trees и общие nearest ranks дают точные пороги без
загрузки всех значений в память. Баллы и сегменты финализируются по одному
клиенту после вычисления общих порогов.

STRICT = F + sold; EXTENDED = F + sold + CP. Окна календарные 12/24/48M,
RUB/KZT независимы. Неполное покрытие/ненадёжная recency/неполные деньги
дают UNSCORABLE и NULL недоступных показателей или баллов по существующему
ядру. OUTSIDE_BASE и NOT_IN_CURRENCY_BASE сохраняются. Часть известных денег
не подменяет полную Monetary; известные суммы всей истории доступны отдельно
в колонках buyer_metrics. Возвраты не вычитаются. Короткое окно с F=0 при
наличии базы 48M обрабатывается существующим RFM, включая сегмент INACTIVE.
Backend не оставляет персональный RFM в NOT_COMPUTED.

Синтетические тесты сравнивают thresholds/populations, распределения R/F/M,
score_counts и segments с RfmAggregates для всех 12 размерностей, полного
и разрывного покрытия. Golden SHA-256 результатов агрегата зафиксированы
по исходной версии ядра; тесты не вызывают Git. Изменение event_period не
меняет клиентские показатели и fingerprint общей RFM-популяции.

## Customers и реальные идентификаторы

Customers открывается только read-only, с query_only/BEGIN и проверкой схемы,
rollback-header и отсутствия незавершённых sidecar. Источник необязателен;
непригодная существующая БД вызывает отказ, отсутствующая — SOURCE_UNAVAILABLE.
По id профилей сохраняются только ссылки на кандидатов выбранных владельцев.
Контакты и raw профиля читаются поздно, при потоковой записи clients.csv,
и не сохраняются во временную SQLite. select_profile из 01A выбирает профиль;
одинаковый email разных ID не объединяет покупателей. Отсутствующий профиль
сохраняет покупателя с NULL контактами. Неоднозначные профили дают CONFLICT,
контакты NULL; произвольного выбора нет. Источник уже содержит один snapshot
на ключ и не позволяет восстановить ранее перезаписанные конфликты.

Профили — текущий snapshot, не исторические контакты на as_of. Это явно
обозначено в manifest. Email/SMS permission остаются UNKNOWN независимо
от наличия контактов и subscriptions. Никакие сообщения не отправляются.
Mindbox ID, source aliases и product ID сохраняются как строки, включая
длинные числовые ID и ведущие нули; SID статистического INDEXED не используются.

## Память, диск и права

temporary_root должен существовать на локальном writable NTFS D:, вне всех
репозиториев, источника и синхронизированных каталогов; private ACL задаётся
администратором/пользователем заранее. Backend не исправляет права общего root.
Проверяются его ACL, доверенность namespace и отсутствие symlink/junction.
Небезопасный root или каталог назначения приводит к отказу до чтения Orders.

Создаётся уникальный detail-<random> каталог с private ACL. Только в нём:
state.sqlite и возможные state.sqlite-journal/-wal/-shm. Настройки DELETE,
FULL, foreign_keys, cache 8 MiB и ограничение page_count. Запросы используют
индексы по customer/ordinal и histogram; сортировка всей истории в RAM не нужна.
Contacts во временной БД отсутствуют, но реальные ID и факты покупок чувствительны.

В Python не накапливаются все покупатели, raw Orders или CSV-строки. Есть
состояние одного клиента, одна исходная запись заказа с её позициями, небольшие
пороги/буферы и штатный CustomerIdResolver, который хранит карту слияний.
Поэтому память зависит от размера крупнейшего заказа и карты CustomerMerges;
полностью постоянная память для произвольных источников не гарантируется.
Тест с 1500 синтетическими заказами и 3000 позициями контролирует Python peak
<24 MiB; это не benchmark и не оценка RSS SQLite/Windows для реального объёма.

Источники читаются O(N); временные SQLite B-trees добавляют O(log U) на вставку,
объём диска растёт с количеством фактов/выбранных строк и покупателей. Отдельный
постоянный индекс не строится. Уменьшение event_period уменьшает CSV, но не
объём необходимой истории для персональных показателей/глобальных порогов.

Перед началом, на этапах, периодически в циклах/SQLite callback и по объёму
записи проверяются свободное место обоих томов, резерв и общий лимит временного
состояния плюс ZIP. При ненадёжной оценке используется fail-closed контроль,
а не прогноз размера по canonical. Небольшая погрешность между проверками
сохраняется; резерв должен учитывать конкурирующие записи на томе.

Настройка прав ограничена новыми собственными объектами, subprocess имеет
timeout 30 секунд; политика проверки используется существующая из
statistics_storage_safety. В окружении Codex PowerShell 7 тесты запускались
с процессным PSModulePath штатных модулей Windows PowerShell 5.1:
SystemRoot/System32/WindowsPowerShell/v1.0/Modules. Это устраняет конфликт
унаследованных модулей при запуске powershell.exe; системные настройки не менялись.
Если ACL helper недоступен, экспорт прекращается, проверки прав не обходятся.

## CSV, manifest и публикация

CSV пишутся непосредственно в ZIP потоком, без отдельных файлов CSV:
UTF-8 BOM, разделитель ;, CRLF, стабильные заголовки 01A. NULL = обратимый
токен \N, не пустая строка. Каждое текстовое поле имеет ровно один служебный
апостроф; это защищает от формул и сохраняет ID. decode_csv_text удаляет его
обратно по схеме. Числа Decimal — точная фиксированная запись, bool — 1/0,
даты/UTC datetime — ISO 8601. Повторный префикс не удаляется произвольно.

Manifest не содержит отдельных ID/контактов. В нём версия, даты, периоды и
покрытие, состав политик, counts, схемы/кодирование, признаки качества,
версии алгоритмов, hash source snapshot и общей RFM-популяции, PII-warning.
Source token связывает catalog, метаданные всех частей и Customers version
под publication lock; это не криптографическая повторная проверка всего raw.
После формирования проверяются версии источника и алгоритмов. Обычный
canonical publisher не может заменить источник при удерживаемом lock;
произвольная враждебная запись доверенным пользователем вне этого протокола
не является гарантией snapshot isolation всего файлового дерева.

В каталоге destination создаётся собственный exclusive private
.statistics-detail-<random>.partial. ZIP64 разрешён; CRC каждого entry
проверяется потоковым чтением готового ZIP. Затем закрываются источники,
удаляется собственное состояние SQLite и проверяются принадлежность partial,
идентичность parent/destination. Только после этого os.replace атомарно
публикует ZIP в том же каталоге, в том числе если том назначения отличается
от D:. Предыдущий destination до публикации не удаляется.

Отмена проверяется при чтении, обработке, финализации, записи и перед replace.
Стадии: source_validation, history, personal_metrics, rfm, clients, orders,
order_lines, zip_verification, atomic_save. Точный процент не обещается.
Исключения/отмена закрывают генераторы, handles и БД в finally. Cleanup
проверяет root/folder/file identities, разрешённые имена и отсутствие reparse;
удаляет только объекты текущей операции. При подмене или отказе удаления
возвращается технический путь; ZIP не публикуется. Удаление файла не означает
гарантированного физического уничтожения информации на SSD.
