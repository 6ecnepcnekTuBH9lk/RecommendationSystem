# Исследовательский прогноз в карточке покупателя (02E)

Существующая секция карточки после активности и перед BPR-MF показывает сохранённый
прогноз оформления заказа, а не оплаты. Дата признаков — 01.09.2026, горизонт —
до 01.10.2026 исключительно. Это исторический эксперимент, не текущая вероятность.
Обучение, scoring и публикация из GUI отсутствуют.

## Поток данных

`CustomerCardWorker` последовательно выполняет прежнюю загрузку карточки, optional
activity и optional propensity. Профиль по-прежнему поступает отдельным сигналом.
`CustomerCardResult.propensity` — необязательное поле immutable контракта.
SQLite, ключ и проверка источников доступны только worker. Форматирование вынесено
в `customer_propensity_presentation.py`; widgets не обращаются к источникам.

`CustomerCardService.load_propensity()` принимает только согласованный canonical ID
из актуального профиля/однозначного contact match. Отличающийся canonical ID BPR
блокирует прогноз; отсутствие клиента в модели BPR его не блокирует. Введённые
контакты и `model_user_id` непосредственно в HMAC не передаются.

`CustomerPropensityService` проверяет published manifest, SHA256, schema/integrity
небольшой predictions SQLite, модель, manifest inference-датасета, current pointer,
source version, history generation и тот же canonical merge graph, что builder v2.
Проверка integrity большой базы истории **не выполняется**. Начальная проверка
артефакта кешируется; затем контролируются файловые версии и snapshot источников.
Lookup использует существующий read-only `PredictionStore` и первичный ключ.

## Ключ

Используется один существующий ключ BUILD-01. Приоритет путей:

1. Явный аргумент `CustomerPropensityService(key_path=...)`.
2. Абсолютный `key_file` в локальном ignored файле
   `user_settings/customer_propensity.json`, относительно корня проекта.
3. Если настройки нет — прежний
   `Path.home()/AppData/Local/KANZLER-AI/propensity-secrets/propensity-v2.key`.

Настройка содержит только путь, никогда секрет или key_id. Путь к файлу настроек
не зависит от cwd. Повреждённая настройка, относительный путь или отсутствующий
указанный ключ закрывают показ без fallback. Чтение настройки и ключа происходит
на worker. После изменения настройки требуется перезапуск приложения.

В KEYFIX-01 подтверждено: AppData при сборке из пакета Codex виртуализирован в
`AppData/Local/Packages/OpenAI.Codex_2p2nqsd0c76g0/LocalCache/Local/`.
PyCharm этот файл по прежнему логическому пути не видит. Локальная настройка
теперь указывает на физический файл **того же исходного ключа** внутри LocalCache;
его доступность и совпадение key_id проверены непосредственно через PyCharm Run.
Ключ не перемещён и не скопирован. Изменение/удаление пакета Codex может повлиять
на сохранность LocalCache: необходима защищённая резервная копия исходного ключа.
В этой задаче резервное копирование не выполнялось.

Автоматического поиска других ключей, создания и fallback нет. Перенаправленный
`LOCALAPPDATA` sandbox не используется. Перед чтением проверяются права доступа:
Windows ACL допускает текущего пользователя, SYSTEM и Administrators.

Алгоритм строго совпадает с builder v2:

```text
key_id = HMAC-SHA256(secret, b"kanzler-propensity-key-id-v1")
pseudonym = HMAC-SHA256(secret, b"kanzler-propensity-customer-v1\0" + canonical_id.encode("utf-8"))
```

`key_id` проверяется constant-time сравнением. Дополнительной нормализации нет.
Секрет остаётся только в памяти сервиса; таблица соответствий и диагностические
логи идентификаторов/псевдонимов не создаются. Нет ключа — `KEY_UNAVAILABLE`.

Причина доступна как безопасный код `key_error` и warning в журнале:
FILE_NOT_FOUND, ACCESS_DENIED, INVALID_FORMAT, CONFIG_INVALID, UNSAFE_ACL,
ACL_CHECK_FAILED, ACL_CHECK_TIMEOUT, ACL_CHECKER_UNAVAILABLE, FILE_CHANGED,
READ_FAILED. Несовпадение key_id — STALE / KEY_ID_MISMATCH. Текст OS-ошибок,
путь, secret, key_id и pseudonym в этих сообщениях не печатаются.

## Состояния и жизненный цикл

Доменный контракт: READY, WARNING, NOT_FOUND, NOT_READY, STALE,
IDENTITY_NOT_CONFIRMED, KEY_UNAVAILABLE, ERROR, CANCELLED. Ошибка/отсутствие никогда
не превращаются в 0%. Все unavailable состояния имеют отдельные пояснения.

Новый поиск, отмена и shutdown сразу очищают старую вероятность. Сохраняются
существующие request_id, последовательный worker, coalescing и повторная проверка
после первого GUI handoff. При смене источников/ключа/артефакта результат становится
STALE. Отмена кооперативная: уже начатая проверка/чтение может завершиться, но её
результат отменённого запроса не применяется; принудительного terminate нет.

NEAR_ZERO_WITH_RECENT_FAVORITE заменяет основное число на «Оценка ненадёжна».
LOW_INDIVIDUALIZATION оставляет число с предупреждением «Недостаточно
индивидуальных сигналов». Недоступность исторического покрытия объясняется
отдельно. Сохранённые вероятности не меняются; бизнес-пороги не назначаются.

## Проверки и ограничения

Новые тесты: `tests/test_customer_propensity_service.py` (28) и
`tests/tabs/test_customer_propensity_ui.py` (25). Реальные данные используются
только в ограниченном локальном probe без выгрузки идентификаторов.

Результаты 02E находятся в `filtered_data/.propensity-02e-20261020/REPORT.md`.
Визуальные снимки получены offscreen Qt из настоящей карточки с явно синтетическими
сервисами, в обеих темах при ширине 600 и 1400; это не снимки рабочего desktop.
Первый этап propensity на проверенной машине занял около 10,6–10,7 с, тёплый —
39–40 мс. Первый поиск целиком занял около 19 с, включая прежнюю загрузку профиля.
GUI оставался отзывчивым. Отдельный показ BPR до завершения optional этапа не
добавлялся: карточка использует существующую финальную доставку результата.

Известные ограничения модели 02C/02D сохраняются. Автоматических маркетинговых
действий нет. Полноценный ручной проход по desktop-приложению остаётся отдельной
приёмочной проверкой; новые тесты и Qt-рендер не подменяют её.
