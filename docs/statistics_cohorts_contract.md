# STAT-COHORTS-CORE-01 — контракт когорт и повторных покупок

## Область ответственности

`Application/statistics_cohorts_core.py` — самостоятельное потоковое расчётное
ядро. Оно принимает готовые `PurchaseOrderFact`, не читает источники, не
адаптирует строки, не разрешает CustomerMerges и не классифицирует статусы заново.
Production PURCHASE, общий DTO, кеш версии 10, provenance, GUI/XLSX/HTML и
существующие расчётные модули не изменены. Новых зависимостей и баз данных нет.

## API и входной контракт

```python
from datetime import date
from Application.statistics_cohorts_core import CohortAggregates

cohorts = CohortAggregates(
    date(2026, 10, 30),                 # обязательная включительная UTC-дата
    orders_coverage,                   # только Orders, без пересечения с Actions
    identity_space=prepared_space,     # такое же пространство, как у фактов
    cohort_start="2024-01",            # необязательно, включительно
    cohort_end="2025-12",              # необязательно, включительно
    check=check_cancelled,             # необязательно; выбрасывает исключение
)
for prepared_fact in selected_unique_order_facts:
    cohorts.add(prepared_fact)
result = cohorts.result()
```

`policies` — необязательное непустое подмножество STRICT_COMPLETED и
EXTENDED_COMPLETED, по умолчанию обе политики. Порядок политик в результате
всегда STRICT, EXTENDED независимо от порядка аргумента.

Нужна именно `date`, а не строка или `datetime`. Системная дата не используется.
Дата должна позволять представить следующий день, H365 и все границы M12;
непредставимые крайние даты отклоняются. Некорректные месяцы и обратные границы
отображения отклоняются.

Вызывающий код обязан передать всю доступную предшествующую историю Orders до
отсечения, включая заказы до начала отображаемого периода. `cohort_start/end`
ограничивают только выходные когорты: более ранние покупки не отбрасываются из
внутреннего состояния и не превращают старых покупателей в впервые наблюдаемых.
Ограничения номенклатуры и Actions здесь неприменимы.

Каждый заказ передаётся один раз после штатного выбора первого снимка. Факт
содержит все строки выбранного заказа до товарного фильтра. Ядро не выполняет
source deduplication: повторные/изменённые снимки одного order ID нарушают входной
контракт. Даже snapshot, не принимаемый покупательской политикой, должен быть
отобран вызывающим кодом до применения политики; нельзя заменять его последующим
покупательским снимком. Не добавлять отдельный набор всех order ID в ядро.

Проверяется тип PurchaseOrderFact, единое явное пространство идентичностей,
валидные private customer/order ID (непустая строка без краевых пробелов либо
положительное int, не bool) и timezone-aware UTC timestamp заказа. Несовпадение
пространств REFERENCE/INDEXED или поколений — ValueError до изменения состояния.
Будущие факты игнорируются и подсчитываются в quality.facts_after_cutoff.

## Когорты и порядок заказов

Ключ `YYYY-MM` — UTC-месяц **первой наблюдаемой покупки** по выбранной политике.
Это не доказанный месяц привлечения нового клиента компании. Более ранних
покупок могло не быть в предоставленной истории или в пробелах покрытия.
`lifetime_first_purchase_proven` всегда false.

STRICT_COMPLETED принимает уже подготовленный результат F + sold;
EXTENDED_COMPLETED — F + sold + CP. Поэтому один покупатель может оказаться в
разных месяцах по двум политикам. Return, отмены и delivering сами по себе не
образуют покупку. Допустимая F-позиция рядом с Return оставляет один покупательский
заказ. Количество позиций, единиц, цена и валюта не умножают число заказов.

Первая и вторая покупки — два минимальных уникальных заказа. Сравнение:
`(order_datetime_utc, тип order_id, order_id)`; int идёт перед str, внутри типа —
обычный порядок значений. При равных timestamps два различных ID дают две
покупки с интервалом 0. Это служебный детерминированный tie-break, не бизнес-вывод
о фактической последовательности одновременных заказов.

Порядок поступления фактов не важен. В памяти сохраняются только первые два
ключа и битовая маска месяцев. При поступлении более ранней покупки основание
маски смещается; уже отмеченные поздние месяцы сохраняются. Заказы после второй
важны для retention, но не для интервала до второй покупки.

## Покрытие и отсечение

Coverage принимает пары timezone-aware ISO timestamp (Z или offset) либо datetime.
Интервалы полуоткрытые `[since, until)`, сортируются, переводятся в UTC;
пересекающиеся и смежные интервалы объединяются штатным shared_intervals.
Naive/невалидные/нулевые/обратные интервалы отклоняются. Полночь после as_of_date
— исключительная верхняя граница расчёта. Входное нормализованное покрытие
сохраняется в source_coverage, обрезанное этой границей — в effective_coverage.

None означает отсутствие метаданных покрытия, [] — объявленное пустое покрытие;
оба варианта не доказывают отсутствие покупок. Различие сохранено флагом
coverage_metadata_available. Пустой результат содержит метаданные и пустые
cohorts, а не придуманную матрицу нулевых покупателей.

Coverage сертифицирует полноту наблюдения, а не допустимость отдельного
наблюдаемого события. Подготовленные факты вне сертифицированных интервалов
сохраняются как наблюдаемые; их число (один раз на факт, не на политику) отражено
в observed_purchase_facts_outside_coverage. Это не расширяет effective_coverage
и не делает такие периоды полностью наблюдаемыми. Вызывающий код отвечает за
подлинность и совместимость фактов с выбранным снимком.

## Вторая покупка и горизонты

`days = (second_utc_date - first_utc_date).days`, то есть календарные UTC-дни,
а не число прошедших 24-часовых интервалов. Горизонты H = 30, 60, 90, 180, 365:
`0 <= days <= H`. День H включён; два разных заказа в один день дают 0.

Для полной наблюдаемости консервативно требуется весь календарный период
`[первая UTC-дата 00:00, первая UTC-дата + (H + 1) дней 00:00)`.
Таким образом день первой покупки также должен быть полностью покрыт; начало
покрытия в середине этого дня не объявляется полным горизонтом.

Для каждого горизонта:

- cohort_size — все покупатели выбранной когорты;
- eligible — горизонт завершён к as_of_date и весь период покрыт;
- repeated — вторая наблюдаемая покупка в пределах H **только среди eligible**;
- observed_repeated — такое событие среди всех покупателей когорты;
- observed_repeated_ineligible = observed_repeated - repeated — подтверждённые
  положительные события вне базы основной доли;
- censored — последний включённый день горизонта ещё позже as_of_date;
- coverage_incomplete — непокрытые интервалы в уже прошедшей части горизонта;
- censored_and_incomplete — пересечение двух предыдущих групп;
- confirmed_without_event = eligible - repeated;
- repeat_rate = 100 * repeated / eligible, либо None при eligible = 0.

Будущая часть периода сама по себе не считается пробелом coverage. При
цензурировании проверяется покрытие только до конца as_of_date. Счётчики могут
пересекаться, но их согласованность проверяема:

```
cohort_size = eligible + censored + coverage_incomplete - censored_and_incomplete
0 <= repeated <= eligible
observed_repeated = repeated + observed_repeated_ineligible
```

Ни покупатель с незавершённым горизонтом, ни покупатель с пробелом не попадает в
«достоверно не вернулся». Положительное наблюдение при пробеле подтверждает
повторную покупку, но не доказывает, что именно это была фактическая вторая
покупка в истории: в пробеле могла скрываться ещё более ранняя.

**Монотонность:** observed_repeated_30 <= ... <= observed_repeated_365. Числители
repeated основной доли и сами доли могут уменьшаться, поскольку eligible для
более длинного горизонта меняется. Например, через 30 дней после первой покупки
ранний повтор уже входит в repeated_30, но покупатель ещё не eligible_60.
Нельзя одновременно требовать монотонность этих числителей и строгую отдельную
базу полностью наблюдаемых покупателей для каждого H.

second_purchase_days содержит число повторных покупателей, распределение
`[[days, buyers], ...]`, среднее и медиану наблюдаемых интервалов. Сюда входят
все наблюдаемые вторые покупки до отсечения, в том числе позднее 365 дней.
coverage_incomplete_buyers отмечает интервалы первая–вторая с пробелами.
Это описательная статистика наблюдаемых событий, не оценка истинного времени
возврата с поправкой на цензурирование. При пустом распределении mean/median=None.

## Retention M0–M12

retention — упорядоченный список из 13 объектов с month_offset=0..12.
M0 содержит kind=COHORT_SIZE и buyers=cohort_size: это размер когорты, не доля
повторной покупки, поля retention_rate в M0 нет.

Для M1–M12 month задаёт соответствующий календарный UTC-месяц, а kind равен
MONTHLY_ACTIVITY. Покупатель учитывается не более одного раза в месяце независимо
от числа заказов. Активность в M2 не подразумевает активности в M1.

Проверяется весь месяц `[первое число, первое число следующего месяца)`.
Знаменатель eligible — только покупатели с полностью завершённым и полностью
покрытым месяцем. Внутри одной строки-когорты календарные границы общие, поэтому
eligible равен cohort_size либо 0; в pooled summary эти значения суммируются.
Пробел в M1 не делает автоматически недостоверным полностью покрытый M2.

Поля аналогичны горизонтам: active (числитель только eligible), observed_active,
observed_active_ineligible, censored, coverage_incomplete,
censored_and_incomplete, confirmed_without_event, retention_rate и status/reasons.
retention_rate = 100 * active / eligible; при eligible=0 — None. Ноль допустим
только при достоверном ненулевом знаменателе и отсутствии наблюдаемой активности.
Незавершённые или ещё не наступившие месяцы не получают ложного нулевого retention.

## Формат результата и сводки

Верхний уровень: as_of_date, cutoff_exclusive, cohort_definition,
source_coverage, effective_coverage, cohort_bounds, horizons, month_offsets,
policies и quality. Все даты — ISO; числовые счётчики — int, проценты — float
либо None. Объект JSON-совместим и пригоден для будущего DTO, но сейчас к нему
не подключён. Вложенные списки/словари — свежие копии при каждом result().

Для каждой политики возвращаются:

- base_buyers: все наблюдаемые покупатели политики;
- displayed_buyers и hidden_buyers: применение только границ отображения;
- cohorts: отсортированный словарь YYYY-MM → cohort_size,
  observed_repeat_buyers, second_purchase_days, horizons и retention;
- summary: те же метрики по отображаемым когортам, cohort_count и cohort_size.

horizons индексируется строками "30", "60", "90", "180", "365".
Сводные доли — отношения сумм числителей и знаменателей, не среднее процентов
когорт. Summary.retention объединяет одинаковые возрастные смещения M1..M12
разных календарных когорт, поэтому в этой сводке отдельного поля month нет.

Status: FULL — все покупатели eligible; PARTIAL — только часть; UNAVAILABLE —
ни одного eligible; NO_BUYERS — размер базы 0. Reasons содержат RIGHT_CENSORED
и/или ORDERS_COVERAGE_INCOMPLETE. quality отдельно предупреждает об ограничении
первой/второй наблюдаемой покупки и возможных скрытых заказах в пробелах.
Customer/order ID, identity_space и внутреннее состояние в результат не входят.

## Отмена, память и сложность

check() вызывается до add(), при обходе покупателей, когорт и месяцев, в начале
и конце result(). Исключение отмены распространяется. После отменённого result()
состояние неизменно, можно повторить финализацию. Отмена до add() не потребляет
факт; между изменениями STRICT/EXTENDED check не вызывается, чтобы одна отмена
не разделяла политики по одному заказу. Это однопоточный накопитель, не объект
для конкурентного add()/result().

B — покупатели, M — максимальный разброс месяцев покупок покупателя, N — факты,
K — объединённые интервалы покрытия, C — выводимые когорты, P <= 2 — политики.
Состояние — O(P * B * M) бит плюс два ключа заказа на покупателя, O(K) метаданных;
ни заказов целиком, ни строк, ни JSON, ни профилей и контактов не сохраняется.
Точнее маска занимает ceil(M / размер машинного слова) слов. Операции над Python
bigint при большой маске не строго O(1): add требует до O(P * ceil(M/word))
и O(log K) проверки покрытия. В типичной короткой истории это небольшой bigint.

result() повторно обходит только компактное состояние: O(P * B * (5 log K + 13
операций с маской)), затем O(C * 12 log K) месячных проверок и сортировку ключей
когорт и различных наблюдаемых интервалов. Полный список N заказов не сортируется
и не перечитывается. Выход и временные агрегаты пропорциональны C и числу
различных наблюдаемых интервалов до второй покупки, не товарным позициям.

## Будущая интеграция — отдельная задача

Точка подключения — Application/dataset_statistics.py, _calculate_statistics():
уже существующая фабрика purchase_fact(raw, lines, ordered_at) строит общий
PurchaseOrderFact после выбора снимка и канонизации. Новый потребитель должен
получать тот же подготовленный факт в общем Orders-потоке до товарных фильтров.
Не строить второй факт и не выполнять повторный source scan.

Текущие ветки buyer_aggregates ограничены customer_filter, RFM — LAST_48M;
ни одна автоматически не гарантирует всю историю для когорт. При интеграции
понадобится общий однократный выбор snapshot на полном Orders-покрытии для
когорт до этих ограничений и совместное использование prepared_fact. Нельзя
вставить cohorts.add() только в scope_order() или внутрь 48-месячной RFM-ветки:
это ошибочно переопределит первую наблюдаемую покупку для старых клиентов.

Отдельно требуется решить контракт DTO/валидации, режимы REFERENCE/INDEXED,
полноту исторического покрытия выбранного поколения, provenance/версию кеша и
представление диагностических числителей, знаменателей и None в GUI/экспорте.
Исторический snapshot отражает выбранное состояние заказа, не хронологию всех
его статусных переходов; ядро не восстанавливает отсутствующие снимки, lifetime
покупки, события из пробелов или фактическую дату завершения заказа. Timestamp
берётся из firstAction.dateTimeUtc, а не из даты оплаты/доставки.

COHORTS-UI, перестроение INDEXED и расчёт реальной истории в эту задачу не входят.
