# STAT-RFM-UI-01: интеграция RFM

RFM использует неизменённое `statistics_rfm_core.py`. Математика, квантильные
пороги, правила равных значений и приоритеты сегментов сохранены.

## Один поток, три временные области

`dataset_statistics._calculate_statistics()` создаёт RfmAggregates по настоящему
покрытию Orders и отдельной дате отсечения. На каждом raw occurrence сбрасываются
два локальных буфера: адаптированные строки и PurchaseOrderFact. Вызов адаптера
и построителя факта выполняется лениво, максимум один раз на occurrence,
нужный хотя бы одной области. Один объект факта передаётся подходящим накопителям.

- Legacy-ветка сохраняет прежний normalized analysis_filter, snapshots и счётчики.
- BuyerAggregates сохраняет исходный customer_filter и собственное покрытие Orders.
- RFM выбирает собственные первые снимки в LAST_48M независимо от начала
  пользовательского периода, общего пересечения с Actions и товарного фильтра.

Компактный `rfm_orders` содержит только выбранные order ID на время расчёта.
Первый допустимый снимок выбирается до проверки STRICT/EXTENDED. Return в первом
снимке не заменяется поздним F. Один order ID может иметь разные первые снимки
в RFM-окне и коротком пользовательском периоде: это разные временные области,
не повторный учёт внутри одной из них. Конфликтующие/идентичные legacy-счётчики
по-прежнему принадлежат старому snapshots и не изменяются новым set.

REFERENCE читает canonical Orders один раз. INDEXED сохраняет ORDER BY id и
расширяет существующий SQL UNION дат LAST_48M, не теряя прежние exceptional rows.
Дата RFM задаётся драйвером до открытия Orders cursor. Позиции не ограничиваются
selected_items; товарный фильтр остаётся только в legacy-ветке после маршрутизации.
Новая схема SQLite и повторное чтение Customers не нужны.

## Дата отсечения

Исходная пользовательская end_date имеет приоритет, используется включительно
и не нормализуется к общей истории. При отсутствии end_date используется
последняя дата доступного покрытия Orders не позднее UTC-даты calculated_at.
Каждый интервал покрытия обрезается началом следующего за этой датой дня;
выбирается максимальная доступная правая граница минус микросекунда. Так будущий
изолированный интервал не превращает разрыв перед ним в доступную историю.
Последняя фактическая покупка и локальная дата демографии отсечение не определяют.

Без доступной даты покрытия и без выбранной end_date результат RFM равен None.
При явной end_date и отсутствии Orders ядро возвращает окна NONE с наблюдаемой
пустой базой, а не подтверждённое отсутствие покупателей компании. Явная будущая
end_date сохраняется как выбранное отсечение; автоматический режим ограничен
датой расчёта. Границы календарных окон и ограничения диапазона date — по контракту ядра.

## DTO, валидация и кеш

Добавлено одно необязательное поле `DatasetStatistics.rfm_statistics: dict | None`:
это непосредственно aggregate-only `RfmAggregates.result()` с as_of_date,
windows и policies. Персональные идентичности, order ID и внутреннее состояние
накопителя не сериализуются. Точные распределения — гистограммы значений с
количествами, без связи с клиентами.

`statistics_rfm_validation.py` проверяет закрытые ключи всех уровней, контекст
отсечения/покрытия, типы и конечность, гистограммы, суммы и знаменатели,
сегменты/UNSCORABLE, score_counts, пороги и взаимосвязи четырёх окон. Используются
готовые чистые функции ядра для проверки эмпирических границ; новых формул нет.
Покупательские базы валют постоянны между окнами; покупки валют могут пересекаться
по клиентам, но не складываются как уникальные покупатели всей базы.

Last-successful cache остаётся версии 10. Отсутствующий/None RFM валиден.
Старый результат без поля показывает «Нет данных в сохранённом результате»;
новый расчёт без достоверной даты покрытия показывает недоступность. Открытие,
отображение и экспорт не читают источники и не запускают перерасчёт.

## Provenance

В алгоритмическую подпись включены ядро и валидатор RFM. Старые slices/INDEXED
несовместимы по обычному механизму актуальности; отключения проверок нет.
Для slices дополнительно сохраняется `rfm_as_of` и проверяется соответствие
сохранённого результата этому отсечению. Это предотвращает повторное использование
среза через границу UTC-дня даже при неизменной локальной дате демографии.

`source_version()` исключает rfm_as_of вместе с filter/customer_period/as_of:
смена даты/фильтра меняет результат среза, но не требует нового поколения индекса
с теми же источниками и алгоритмом. Из-за изменения самого алгоритма прежнему
реальному поколению потребуется последующая штатная перестройка. В этой задаче
реальный индекс не перестраивается.

## GUI, XLSX и HTML

`statistics_rfm_presentation.rfm_sections()` строит общий типизированный whitelist
из сохранённых агрегатов. Пересчёта квантилей, фактов и сегментации в представлениях
нет. Суммируются лишь готовые score_counts по компонентам для отображения
распределений баллов; значения порогов берутся из DTO.

GUI добавляет RFM после покупательской аналитики во вкладке «Клиенты»:

- дата отсечения, календарные границы, фактические интервалы и полнота покрытия;
- общая наблюдаемая база, активность и денежная полнота;
- отдельные валютные основания, известные суммы и полная Monetary;
- сегменты с долями валютной базы и пояснениями, включая UNSCORABLE;
- распределения баллов и сохранённые пороги с численностью основания;
- сравнение двух 12-месячных периодов и компактное STRICT/EXTENDED.

XLSX получает отдельный лист «RFM-анализ» после прежних листов. Денежные значения
передаются числами, даты — датами, подписи — строками. Действуют обычные ограничения
числовой точности Excel. HTML сохраняет шесть существующих разделов навигации,
RFM добавлен внутри клиентов. Offline-работа, сортировка, адаптивность и прежние
графики сохранены. Все три представления показывают одинаковые исходные агрегаты.

Покрытие FULL/PARTIAL/NONE и неизвестные значения подписаны явно. Наблюдаемый F=0
отделён от подтверждённого отсутствия покупок; при неполной истории последнее
недоступно. Известный подытог не называется полным оборотом. Денежная полнота
общей базы и валютные основания показываются отдельно, без сложения валют.

## Проверки и ограничения

Используются только синтетические источники: parity, один reader/adapter/fact,
дедупликация на границах, короткий период и 48-месячная история, алиасы, Orders
вне Actions, пропуски покрытия, недоступные деньги, валидация, schema-10 roundtrip,
UTC-отсечение/provenance и отображение/экспорт без источников. Сохранность старых
полей, включая buyer_statistics, проверяется при включённой/отключённой RFM-маршрутизации
и прежними golden-тестами. Обе темы проверяются на синтетическом результате.

RFM требует адаптируемых исходных заказов в расширенной области: некорректные
source-поля могут остановить весь расчёт, как и прежние source adapters. Ошибка
не подавляется, неполный успешный результат не публикуется. UNKNOWN_CURRENCY
и INVALID_PRICE, представимые готовым фактом, сохраняют правила ядра; новая
интеграция не обходит строгую проверку raw на границе адаптера.

Память дополнительно содержит RFM-числовые состояния по покупателям/окнам и
set выбранных order ID; полные истории не сохраняются. Покрытие не доказывает
lifetime-полноту, статусы снимков не подтверждают оплату/передачу товара,
CP остаётся сравнительной политикой. Когорты и персональные выгрузки не добавляются.

Итоговая проверка: один расширенный релевантный прогон — **759 passed**;
отдельно модуль вкладки статистики — **81 passed**. Включены 46 новых проверок
интеграции/представлений (35 + 11) и прежние 73 теста ядра. Ruff для всех 19
затронутых Python-файлов и whitespace-проверки пройдены. Восемь синтетических
снимков GUI и примеры XLSX/HTML сохранены; проверены обе темы и одинаковые значения.
Сверка 328 исходных/защищённых файлов выявила только 16 ожидаемых изменений;
добавлено пять файлов. Ядро RFM, политики/факты покупок, BuyerAggregates,
реальный last-successful cache и canonical/catalog.json остались побайтно прежними.
Массовые GUI/evaluation-прогоны, пересчёт реальной истории и реальная перестройка
INDEXED не выполнялись. Изменения оставлены в рабочем дереве без staging/commit/push.
