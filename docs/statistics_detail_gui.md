# STAT-DETAIL-EXPORT-01B2 — GUI детальной выгрузки

Новая кнопка «Экспорт данных покупателей» находится справа от прежней
«Экспорт статистики» на вкладке статистики. Старый агрегированный XLSX/HTML ZIP
сохранён. Длинный основной статус переносится, чтобы новая кнопка не расширяла
строку за обычную ширину окна. Чтение истории и создание ZIP выполняются только
в отдельном Python-процессе. Работа с реальными данными при разработке не запускалась.

## Параметры и предварительная проверка

До открытия диалога inspect_sources читает только catalog.json, метаданные
существующего .writer.lock и имена частей Orders/CustomerMerges. Строки Orders
и Customers не читаются, размеров всей истории не подсчитывают. При отсутствующих
или непригодных источниках показывается SOURCE_NOT_READY, worker не запускается.
Доступность кнопки не зависит от displayed_result; сама вкладка не проверяет
реальные источники автоматически при открытии.

Диалог задаёт начало/конец заказов либо «Вся доступная история», дату оценки UTC,
режим ALL_SELECTED (по умолчанию) либо PURCHASE_EITHER, ZIP и приватный temp root.
Названия режимов русские; возвраты/отмены в ALL_SELECTED объяснены. При текущем
пользовательском периоде предлагаются его даты и окончание как as_of. Без периода
as_of — последняя доступная дата Orders, ограниченная текущей UTC-датой; since/until
трактуются как полуоткрытое покрытие, исключённая верхняя полночь не даёт лишний день.
Диалог позволяет менять параметры, не меняя AnalysisFilter и товарный отбор.
Окончание периода позже as_of отклоняется; будущие относительно as_of заказы
не отсекаются скрыто в GUI.

Пользователь видит назначение периода и обязательный текст о персональных данных.
Идентификаторы и контакты не обезличиваются. Наличие контакта не даёт согласия
на коммуникации. Файл выбирается QFileDialog.getSaveFileName с ZIP (*.zip) и именем
Данные_покупателей_YYYY-MM-DD_HH-MM-SS.zip. Предлагается родитель проекта на D:.
Выбор файла не создаёт ZIP. Штатный диалог подтверждает перезапись; при ручном
вводе существующего пути требуется отдельное подтверждение с ответом «Нет»
по умолчанию. Сам существующий ZIP заменяет только backend после успеха.

GUI выполняет быстрые проверки путей: запрет размещения в Git-проекте,
источниках, canonical, .git/.venv312, индексах/моделях и temp root. Известные
OneDrive/Dropbox/Google Drive и синхронизированные корни из environment отвергаются.
Все reparse/junction и '..' отклоняются до resolve. Сетевые/непригодные тома
и недоверенные ACL дополнительно отвергаются worker/backend до чтения истории.
Определить произвольное стороннее приложение синхронизации по одному пути нельзя;
приватные права не являются шифрованием или защитой от программы текущего пользователя.

## Временный каталог и права

Путь редактируемый; значение по умолчанию:
D:/RecommendationSystem-Private/detail-export-temp для текущего имени проекта.
Он вычисляется из родителя/имени PROJECT_ROOT, а не привязан к C:.
Переменная KANZLER_DETAIL_TEMP_ROOT позволяет задать другой root.

В worker существующий root только проверяется, его права не исправляются.
Недостающие каталоги создаются эксклюзивно после проверки доверенного namespace;
private ACL применяются лишь к созданным этим worker каталогам. Новый приватный
пустой root сохраняется как конфигурационное расположение для следующих операций.
Отмена проверяется между шагами подготовки. При невозможности обеспечить защиту
операция завершается ошибкой; fallback в общий temp на C: отсутствует.
Неизвестные каталоги не удаляются.

Backend сохраняет свою временную SQLite в отдельном owned detail-<random>.
Private partial ZIP создаётся рядом с destination до записи персональных данных.
После проверки ZIP и очистки state публикуется os.replace. Реальный тест на пустом
синтетическом файле подтверждает сохранение private ACL после replace. Постоянный
индекс не создаётся, формат четырёх ZIP-entry и всех 218 колонок не изменён.

## Процесс, IPC и прогресс

DetailExportProcess — маленький самостоятельный QObject, владеющий QProcess.
Это отдельное состояние self.detail_process; self.process обычного расчёта не
переиспользуется. Запуск: sys.executable -u -B scripts/statistics_detail_export.py,
рабочая директория PROJECT_ROOT (D:/RecommendationSystem). Старые Scripts/*.exe
не вызываются. Аргументы содержат только даты, enum, технические пути/лимиты.

stdout — JSON Lines, ASCII-экранирование Unicode, максимум 4096 байт на сообщение.
Допускаются только точные схемы:
- progress: stage из allowlist и неотрицательный integer processed;
- finished: только counts clients/orders/order_lines;
- cancelled: без payload;
- error: безопасный код из allowlist, при отказе cleanup — проверенный technical_path.

Повторные ключи, неизвестные поля/события, недопустимые типы/размеры, незавершённая
строка или второй terminal отклоняются. Произвольный worker-текст не показывается.
Cleanup-путь должен соответствовать имени собственной временной папки/partial
и выбранному root/каталогу назначения; произвольные имена не принимаются.
Вывод backend перенаправлен в discard; logging CLI отключён. stderr не хранится
и не показывается пользователю.

Стадии: source_validation, history, personal_metrics, rfm, clients, orders,
order_lines, zip_verification, atomic_save. Для отдельного rfm добавлен только
progress callback перед штатным finalize; формулы и выборка не изменены.
Callbacks прорежены до 4/с при неизменной стадии; heartbeat раз в 2 секунды
поддерживает наблюдаемость долгой стадии. После terminal heartbeat подавляется.
GUI показывает busy progress bar и количество, не обещает точного процента.

За один проход Qt обрабатывает не более 64 KiB, затем возвращается в event loop.
stdout buffer ограничен размером одного сообщения. Некорректный поток получает
запрос кооперативной отмены. Если child продолжает flood stdout/stderr свыше 1 MiB,
он останавливается как аварийный, с предупреждением о возможных остатках.

## Отмена и закрытие

Управление использует приватный stdin pipe собственного QProcess, без общих
cancel-файлов. GUI однократно пишет {"command":"cancel"} с переводом строки;
при ранней отмене запрос отправляется после started. Daemon reader worker
устанавливает threading.Event. Backend проверяет cancelled и выполняет finally.
EOF (в том числе исчезновение parent) также запрашивает отмену. Некорректная
команда даёт CONTROL_PROTOCOL_ERROR после кооперативного завершения.

Нормальная отмена не использует terminate/kill. Кнопка отмены отключается после
запроса; GUI ждёт terminal и фактического process.finished. Отмена имеет exit 2,
ошибка exit 1, успех exit 0. Несовпадение terminal/кода либо CrashExit не считается
успехом. Backend мог уже закончить атомарную публикацию до позднего запроса отмены:
в этом случае GUI сообщает о сохранённом ZIP и прямо объясняет, что отмена опоздала.

Close окна и Quit приложения перехватываются: отправляется отмена, закрытие
откладывается до завершения процесса. Живой QProcess не уничтожается при обычном
закрытии. Через 30 секунд ожидания появляется аварийная кнопка; она сама процесс
не убивает. Принудительный stop требует подтверждения с «Нет» по умолчанию.
После kill/crash нельзя гарантировать выполнение finally: GUI сообщает о возможных
остатках в temp root и .statistics-detail-*.partial рядом с destination, ничего
чужого не удаляет. Полностью опубликованный ZIP мог появиться до аварийной остановки.
Если app teardown уже необратимо начался вне обычных событий Close/Quit, shutdown
сначала даёт 3 секунды на отмену, затем использует аварийный kill/reap.

## Изоляция и ошибки

Во время detail запрещены второй detail, агрегированный расчёт и агрегированный
экспорт из этой вкладки. Во время существующих операций detail недоступен.
Страницы статистики остаются доступны для просмотра. displayed_result, cache,
buyer/rfm/cohort DTO не используются и не записываются. При отказе настройки,
старта, IPC, backend, cancel/crash/force все кнопки восстанавливаются.

Успех показывает фразу «Детальная выгрузка покупателей сохранена», counts и
выбранный путь. CSV автоматически не открываются; передачи по сети нет.
Ошибки объясняются по безопасным кодам: источники, место, права, ACL, I/O,
конфликт snapshots, схема Customers, изменение источника/назначения и cleanup.
Backend точечно классифицирует AdapterError/RawExportError/OrderSnapshotConflict,
PermissionError/ENOSPC/OSError. Исключения и traceback с данными не выводятся.
Расчётные правила RFM/когорт/покупок/денег и формат manifest/CSV не менялись.

## Проверки и ограничения перед реальным запуском

Новые тесты используют mocks, настоящие QProcess с синтетическим протоколом,
маленький синтетический canonical fixture и новые pytest-каталоги D:/CodexTestTemp.
Проверены отдельная кнопка, даты, диалог/перезапись, IPC, отзывчивость, cache/display,
кооперативная/поздняя отмена, Close/Quit, авария, flood и права финального файла.
Первый добавленный тест Quit потребовал исправить bound-method mock QApplication.quit
и экранирование JSON тестового child; production-жизненный цикл менять не потребовалось.

Перед реальным экспортом пользователь должен выбрать доступные canonical-источники,
локальное защищённое назначение, подходящий private root на NTFS D: и достаточно места.
При разработке реальная история не читалась, реальный экспорт/индексация/расчёт
статистики/обучение не запускались. Права реальных выбранных каталогов в этой задаче
не проверялись и не менялись. При запуске из окружения PowerShell 7 может потребоваться
корректный процессный PSModulePath штатных модулей Windows PowerShell 5.1 для Get-Acl,
как описано в документации backend; отсутствие ACL-проверки приводит к отказу.
